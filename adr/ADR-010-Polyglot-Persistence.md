# ADR-010 — Polyglot Persistence: PostgreSQL + MongoDB (+ specialized stores)

**ADR ID:** AD-010 · **Status:** Accepted · **Date:** 2026-07-20
**Part of:** ADR Register — see `000-ADR-Index.md` · **Project:** Reliability-First AI Gateway

- **Status:** Accepted · **Date:** 2026-07-20 · **Decision Makers:** Architecture Council
- **Context:** `04 §44` established polyglot persistence by data class (relational config, append-only audit, time-series metrics, in-memory cache, object storage, streaming log). This ADR selects the **primary database technologies** for the relational and document classes, complementing the specialized stores.
- **Problem Statement:** Which database technologies serve the strongly-consistent relational data and the flexible document/record data?
- **Decision:** Adopt **PostgreSQL** (relational, strongly-consistent) for configuration, tenancy, policy, and accounting reconciliation; and **MongoDB** (document store) for flexible, high-volume semi-structured records (e.g., request/interaction records and flexible telemetry-adjacent documents). These are reached via persistence ports (AD-002) and **complemented** — not replaced — by the specialized stores from `04 §44`: a **time-series store** for metrics, **object storage** (WORM-capable) for large payloads/backups and long-term immutable audit, the **in-memory tier** (AD-008), and the **streaming log** (AD-009). Audit tamper-evidence is a **layered** property (append-only + integrity verification + WORM object storage), not solely a database feature.
- **Decision Drivers:** Match store to access pattern and durability need; strong consistency where correctness demands it; flexible schema for varied records; avoid forcing one store to do everything.
- **Alternatives Considered:** (a) Single relational database for all — rejected: poor fit for high-cardinality metrics, flexible records, and log/stream needs. (b) Single document database for all — rejected: weaker for strongly-consistent relational integrity (config/tenancy/accounting). (c) Other relational engines / other document/wide-column stores (e.g., Cassandra, cloud-native document DBs) — acceptable equivalents behind the persistence ports; selected classes chosen for maturity, consistency guarantees, operational familiarity, and ecosystem.
- **Pros:** Right tool per data class; strong consistency for critical data; schema flexibility for records; each store independently scalable.
- **Cons:** Multiple datastores to operate and secure; polyglot complexity.
- **Trade-offs:** Operational polyglot complexity for correctness and fit — the correct trade for a reliability-first platform.
- **Consequences:** Distinct stores per class; no store on the hot path synchronously (writes are event-driven, AD-005); audit immutability layered across MongoDB/append-only patterns + WORM object storage.
- **Business Impact:** Correctness and audit integrity (`02` BR-011/012). **Engineering Impact:** Persistence adapters per store; polyglot ops. **Security Impact:** Each store encrypted, tenant-scoped, access-audited. **Performance Impact:** Off-hot-path; not a request-path bottleneck (`NFR-DS-001`). **Operational Impact:** Multiple stores to back up, replicate, and monitor.
- **Risks:** Polyglot operational burden; audit-immutability correctness across layers. **Mitigations:** persistence ports, per-store runbooks, layered audit integrity + WORM (`04 §43/48`), test-restores (`NFR-BAK-001`).
- **Affected Components:** Config/Tenant/Policy store (PostgreSQL), Records/flexible store (MongoDB), Audit (layered), Metrics (TSD), Object storage. **Related BR:** BR-011, BR-012, BR-027. **Related NFR:** NFR-DS-001, NFR-AUD-001, NFR-CFG-001, NFR-COST-001. **Related PRB:** PRB-011, PRB-012, PRB-030.
- **Related ADRs:** AD-002, AD-005, AD-009, AD-008. **Review Criteria:** Revisit per-class technology as scale/consistency/operational needs evolve. **Future Revisions:** Store-class substitutions per deployment (behind ports); this is expected and low-risk due to the port abstraction.
